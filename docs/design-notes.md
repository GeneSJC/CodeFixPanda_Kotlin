# Design notes

The decisions and trade-offs behind the code, and the reasons for them, which are too long for a code comment. Code points here by section title.

## Top Repos screen

- **What it shows.** Repos as they fall out of grouping matching issues by parent repo, sorted by match count. Stars, forks, open-issue counts and "updated X ago" are not in an issue-search response, so cards show only the title, the match count and a README preview. That is a deliberate reduction, not a bug.
- **Mode is one whole-app choice.** It is made once at the gate screen. A mode dropdown in the title was tried and removed: it undercut the "you have to choose" framing and was not discoverable. The two "Find Beginner-Friendly Issues" / "Find Projects Asking for Help" menu items switch the mode in place, but sit at the bottom of a menu the user has to open deliberately. They are hardcoded; reusing the gate screen would scale better to a third mode but was not worth the navigation complexity for two. A third mode means editing those two items.
- **Hidden issues.** `uiState.repoGroups` stays the raw cached data; the hidden-filtered groups are derived on every recomposition and never written back. A repo whose issues are all hidden stays in the list with an "All hidden" badge, and leaves only when the cache is cleared. The repo screen gets the raw group so it can show hidden issues and bring them back.
- **Cache actions.** "Check for New Repos" merges fresh results into the list and does not replace it. "Clear Cache" wipes the whole cache (a known limitation, not an oversight), asks for confirmation, says that bookmarks and hidden issues are kept, and reloads the screen afterwards.
- **Load More is manual.** Auto-loading on scroll would spend Search API calls the user did not ask for, so the footer is an explicit tap.
- **Rate-limit chip always renders.** A cache hit never calls the network, so without a placeholder the chip could stay absent for a whole session and then pop in next to the mode's info icon. Numbers normally arrive with the first list (a live search, or a `/rate_limit` lookup after a cache hit). The icon is a fixed drawing; it replaced a key emoji that was too small to read on a phone.
- **Landscape split view.** A landscape phone is short on height, not width. The mode, repo count and language picker move into a narrow independently-scrolling left rail so the card list gets the full height. The language chips wrap in the rail because a horizontally scrolling row nested inside a vertically scrolling column would compete for gestures.
- **Menu groups.** Repo Management, Find Issues, then Sandbox (the dev-only animation replays, deliberately last). The build label is always visible in the menu header, so the running build is easy to identify.
- **README preview on cards.** A plain-text snippet, 2 lines when collapsed, expandable with no extra network call. It renders nothing while loading or when the repo has no README, because a spinner or a "no README" note would be clutter.

## Issue card

- **Actions.** Share opens the system share sheet (one `ACTION_SEND` call, which also covers email: Gmail is one entry in the sheet). Copy Link puts the URL on the clipboard and shows a Toast, which is self-contained: a Snackbar would force every screen that shows a card to supply a host. Bookmark does use a Snackbar, because that was the specific request, and so the caller must pass a `SnackbarHostState`. Having one action on a Toast and one on a Snackbar is a known inconsistency, kept on purpose.
- **Structure.** The revealed row is its own composable, `IssueCardActions`. The card still owns the coroutine scope for the bookmark Snackbar and hands the row an already-wrapped callback, because the row leaves composition when the card collapses and would cancel a scope of its own.
- **Bookmark message.** "Bookmarked" or "Unbookmarked" is predicted from the current `isBookmarked`, which is safe because the in-memory effect of the toggle is synchronous. The disk write happens afterwards, off the UI thread.
- **Hide has no Snackbar here.** The card is about to be removed from the list, which would cancel a coroutine scope tied to it before an Undo could be tapped. The screen owns the hide Snackbar with a scope that outlives any one card.
- **Density.** The repo identity row is gone (the repo name is redundant on a per-repo screen). Labels always show, because a label such as "good first issue" identifies the issue. The actions are collapsed behind a chevron. `expanded` is local state; the screen keys cards by issue id, so it survives recomposition.
- **Chevron animation** is a 300 ms tween, not the README widget's 2 s: it fires on every card in a scrolling list, where a slow animation would feel sluggish. The top-right badge stack (external-link badge above the chevron, a 2 dp gap, a 7 dp top offset) is accepted as it is; it will not line up exactly with a two-line title.

## Repo issues screen

- **No repo description.** An issue-search response has no repo description, so the section that used to sit under the title is gone. That is a visible, deliberate reduction.
- **Refresh footer.** "Refresh this repo" stays reusable: after a refresh a result line appears above the button instead of replacing it. The empty-state message is an item inside the list, so the footer renders either way. It is only reachable after a refresh finds zero issues, since a repo's group is never empty on first load.
- **README is an overlay.** An earlier version gave the README `weight(1f)` in the column and skipped composing the list while it was open. That broke the expand animation, because `weight` forces the child's size on every frame, so the README jumped to full size and the list shifted. Now the list is always composed and full-size inside a Box, and the README is a second Box child with an opaque background, which can animate freely in both directions.
- **README fetch** uses GitHub's Contents API, a different API and quota from search, so it is deliberately not tracked by the rate-limit chip.
- **Header action** opens the repo's GitHub page. It keeps the diagonal glyph, unlike the card's external-link badge (a plain arrow), because it opens a different destination: the repo, not one issue.

## Navigation

- **The welcome comes first.** With no token the start destination is the welcome, then the mode gate, then Top Repos. "Try the demo" always navigates forward, so the welcome stays below it and Back from the demo returns to it, whether the welcome was shown at start or reopened from the menu. A saved token at start drops the welcome, since there is nothing to come back to; saving one on a reopened welcome pops back to where the user was.
- **The gate is a real destination.** An earlier version returned early outside the NavHost; Top Repos was then the only back-stack entry and pressing Back closed the app. That was found by pressing Back on a device.
- **Reset App** is the only way back to the gate once a mode is chosen. It clears the mode and navigates with `popUpTo(graph.id) { inclusive = true }`, wiping the whole back stack; a plain `navigate()` would add a second gate on top of the open screens. Bookmarks, hidden issues and the cache are untouched.
- **Selected repo group and language** are plain Compose state in the nav host, not passed through the route, to avoid serializing the model just to pass it along.
- **Typed navigation: considered, not adopted.** Type-safe routes need the Kotlin serialization plugin (a build change) and a second serialization library next to Moshi. The eight routes (welcome, token guide, mode gate, Top Repos, repo issues, bookmarks, hidden issues, settings) are named constants with no arguments, so the compiler already rejects a mistyped route and there are no hand-built arguments to protect. The host's copy of the selection is acceptable for the reason above. Revisit if a route ever needs arguments.
- **Hidden Issues** is reachable from the Top Repos menu and from the repo screen's "all hidden" state; both push it on top, so Back returns to where it was opened. A separate full-screen README destination was removed when the inline README widget replaced it.

## Top Repos state

- **One call per load.** The list is built from one Search API call for the active mode's label, grouped by parent repo (`repository_url`). A repo appears only if it had a matching issue in the batch, and the ranking is match count only. The old 60-second cooldown went away because one call per load no longer risks the 30-per-minute Search API cap.
- **Load More adds, never appends.** A repo's matches are not guaranteed to land on one page, so naively appending would show it as a second card. New issues are re-grouped against the repos already held, then re-sorted; a repo's rank can legitimately change.
- **Rate-limit event.** A Load More that returns 403 with `X-RateLimit-Remaining: 0` is the Search API rate limit, not a generic error. It emits one `RateLimited` event and leaves `canLoadMore` and `currentPage` untouched, so the button works again after the reset. Events are a `Channel` so each is delivered exactly once, not re-shown to every new collector.
- **Cache-first.** A hit fills the state with no network call, including `currentPage` and `canLoadMore`, so Load More resumes where a previous session stopped. Every successful fetch writes the accumulated groups back. Fresh data is explicit, through "Check for New Repos".
- **Check for New Repos replaced a refresh that lost data.** The old refresh went through `load()` and replaced the whole list with page 1: with 200 repos built from ten Load More taps, one refresh discarded nine taps' worth. The replacement fetches the same page 1 but updates the list in place, and never resets `currentPage`, or the data it exists to protect would be lost another way.
- **Why `syncFromCache`.** Top Repos and the repo screen have no handle on each other's ViewModel. The repo screen writes its refreshed group to the cache, and Top Repos re-reads the cache when it is navigated back to.

## Repo issues state

- **Why it makes no network call on open.** Every issue the screen can show is already in the repo's group; that is what it means for the repo to be on Top Repos at all.
- **Why there is a refresh at all.** The group holds only the matches swept up while Top Repos built its list, bounded by how far Load More had got, so a repo with more matches can look partial. Closed issues can only be discovered this way too, because issue search returns open issues only.
- **The refresh** is one call (`repo:owner/name label:"..." state:open`, up to 100 per page). It replaces the held issues outright, which is right here because the result is the complete live set for the repo, unlike Check for New Repos, which updates from a partial page.
- **Write-back.** A successful refresh updates the Top Repos cache entry the group came from, so the match count agrees on return. An empty result removes the repo from the cache: a repo cannot legitimately be on Top Repos with zero matching issues.
- **The language is passed down** from Top Repos. The refresh needs an exact `LanguageFilter` for the query's `language:` qualifier and for the cache key, and a repo's display language string is not reliably reversible to one.
- **Manual on purpose.** It is an explicit button with a visible cost note, not something that happens automatically.

## Data layer

- **Which storage.** SharedPreferences for single values (the Issue Mode, the token, the start-animation flag); a JSON file in private storage for lists of real objects (bookmarks, hidden issues, the Top Repos cache). Hand-rolling serialization for one enum value would be avoidable complexity. File names have been kept across refactors, so data saved earlier still loads.
- **Writes.** File writes run in order on a single background thread. An earlier version started a thread per write, so two quick changes could finish out of order and leave the older list on disk. A failed write is swallowed on purpose: it never rolls back what the user already saw.
- **Hiding is a display filter.** The hidden-issue repository stores only the ids to filter out; the cached data stays exactly as GitHub returned it, so Unhide is instant.
- **The Top Repos cache** is keyed by (language, mode) and is cache-first, never auto-refreshed. Saving and replacing are read-modify-write over one combined file, so the repository takes a mutex.

## README previews

- **In memory only.** A snippet is cheap to refetch and has no reason to survive process death.
- **Cost.** Each card's first appearance makes one Contents API call, a different and far larger quota (5,000 per hour authenticated) than the 30-per-minute Search API; after a few Load More taps there can be dozens of cards.
- **Retry only on a thrown exception.** An early version marked a repo "handled" the moment it was first requested. Two repos whose README loaded fine on the repo screen never got a preview, because a transient failure during the initial burst of calls left their cards permanently empty. Now only an exception is retried (on a later recomposition); any real HTTP answer, including a 404 for "no README", is final.

## Mode gate

- **A literal gate.** With no mode chosen the app shows this screen instead of a silent default; the mode is one deliberate choice made here.
- **Nested theme.** The screen's content sits in a theme with `issueMode = null`. Tapping a card sets the mode synchronously, so the single root theme recomposed every visible screen, including this one still fading out; the theme's crossfade covers only a handful of color roles, so the subheader and text color visibly snapped to the new mode's tone just before the transition. Pinning this subtree to the neutral scheme removes the snap.
- **Plain names, labels second.** The modes are called "beginner-friendly issues" and "projects asking for help", because GitHub's own labels ("good first issue", "help wanted") mean little to someone outside open-source convention. The descriptions name the labels, and the search queries still use the real ones, so only the words on screen are plain.
- **One info icon, one dialog.** The screen explains itself (the question, the prompt, two buttons), so there are no per-mode descriptions on it. An info icon beside the prompt opens a single dialog (`LabelInfoDialog`) describing both modes for anyone who wants more, and it is the same dialog and wording the Top Repos pill uses, held in one place so they cannot drift. The "Open Source Panda is not affiliated with or endorsed by GitHub." line sits directly under the headline, so it is seen before anything is chosen.
- **The title bar is the app's identity.** The top of the gate is `BrandTitleBand`: the orange gradient, the branch glyph and the panda from the head to the middle of the torso, standing on the band's bottom edge. The name is not written out; it is the band's accessibility description. The band reaches under the status bar, and its height (120 dp) is what shows below it. The glyph is drawn by the shared `BranchGlyph`, the same drawing the splash backdrop uses, so the two cannot drift.
- **The content sits on a soft tangerine.** Under the title bar the screen is a pale tangerine gradient (`BrandSoftBackground`) with the branch glyph in a deeper tangerine, large and bleeding off the right edge. The glyph fades in along the diagonal from the top left (invisible) to the bottom right (60% at most), so it never runs under the headline and is strongest where the screen is empty. The orange stays the title bar's color and the content stays readable, with dark text. The two choices are side by side, equally wide, each the mode's color with the icon above the name, since there are only two.

- **Every plain screen shares the soft backdrop.** The gate, Top Repos, a repo's issues, bookmarks, hidden issues and settings each wrap their scaffold in `BrandSoftBackground` (with a transparent container), so no screen is a plain white or pastel sheet. Each screen opts in on its own, so a screen can later take a different backdrop (the panda, bamboo) without touching the others.
- **Header and backdrop follow the mode.** `BrandTopAppBar` replaces the stock top bar on Top Repos, a repo's issues, bookmarks, hidden issues and settings: a gradient in the mode's color (the brand orange for projects asking for help, the blue for beginner-friendly) with white text and icons, a short bar next to the start screen's taller `BrandTitleBand`. The backdrop takes the same hue (tangerine or a pale blue, with the glyph in a deeper shade). Both come from `ModeDecor`, carried by `LocalModeDecor` from `OpenSourcePandaTheme`, because Material has no color roles for them; a screen asks for "the header" and never names a color. The mode pill on a bar is a see-through white with white text, since its own color would vanish into the bar. The stock icon button takes its color from the theme and not from the bar, so bars use `BrandBarIconButton`. The card, outline and outline-variant roles are set explicitly per mode, so none of Material's stock lavender-gray shows through.

## Splash screen

- **The animation.** The title builds itself: "Open" slides in from the left and lurches as it stops, "Source" slides in from the right and shudders on impact, and "PANDA" rises into place beneath them. Then the panda drops in above the name, falling with gravity, and lands with a squash from its base as a soft burst of light flashes behind it. It plays at half speed so each beat can be seen.
- **Later launches.** Once a device has seen the full animation finish, every later launch plays a short version: the finished title and the panda fade in, sit for a moment, and then the same burst plays, so a returning user is not made to watch the build each time. The short version is its own composable with an independent copy of the ending, so changes to it can never affect the first-launch animation. Both versions draw the same `TitleWordmark` (the panda, the name and "PANDA"), so the short version starts exactly where the full one ends, and they share one burst, `SplashBurst`, which is drawn rather than laid out so that it can grow far past the panda without moving anything.
- **One entry point.** `AppStartSplashScreen` decides which version plays. The cold start and the menu's "Play App Start Animation" replay both call it, so a replay always matches what a user sees.
- **Fixed look.** The splash always uses the brand palette (orange, with the sun-yellow burst), whichever issue mode is active. It is the app's own identity, so it does not repaint when the mode changes. Its backdrop, `SplashBackground`, is the orange gradient with the icon's branch glyph drawn behind the title in Compose, black-outlined and partly transparent. The older coin, origami and shape-stack variants are not the launch splash; they stay pinned to the beginner-friendly blue.
- **The panda art.** The splash and the welcome screen draw `panda_mark.png`, the mascot from the launcher icon art, 512 px tall, so it stays sharp at 130 dp even on the densest screens.

## Color palette

- **Colors have jobs.** The orange, sun yellow and navy are the app's identity (`Brand*` in `Color.kt`), from the launcher icon: the splash, the title bar, the artwork. Two colors stand for the issue mode, which tells you what you are looking at: the blue for beginner-friendly issues and the orange for projects asking for help. The seafoam, the panda's scrubs (`BrandSeafoam`, the same color in the artwork), stands for what you have selected or saved: the chosen language chip and a saved bookmark's star, both with navy text, since white does not pass contrast on it. It is the theme's `tertiary` role, so a screen asks for "the selected color" and does not name a hue. A new screen takes a job for each color and does not add a color.
- **The modes are a blue and an orange.** Beginner-friendly issues use the brand blue (a lighter step of the navy in the panda's outline) and projects asking for help the brand orange, each a strong primary (white text on it passes contrast) with a very light tint of the same hue. Two shades of one hue were tried first and read as too close together, and the purple and green they replaced did not belong to the icon's palette. The baseline scheme (no mode chosen) uses the orange. Every color is a named constant in `Color.kt`; screens do not type hex values.
- **Dark mode is tabled.** `OpenSourcePandaTheme` still has a `darkTheme` parameter and a dark scheme, but it is hardcoded to false and the mode schemes are light-only. There is no setting for it, so nothing is hidden; a dark mode would need a dark scheme per mode first.

## Launcher icon

- **One icon for both flavors.** The icon lives only in `app/src/main/res`, so `foss` and `commercial` share it. The earlier per-flavor overrides were removed because two icons meant two sets of files to keep in step.
- **Adaptive layers in `mipmap`.** Background, foreground and the themed monochrome layer sit beside the legacy square and round icons, and the adaptive definitions (`mipmap-anydpi-v26`) point at them. The launcher shows only the middle 72 of the 108 canvas, so everything that matters stays inside it. The monochrome layer is a solid silhouette because the system tints it with a single color.
- **The branch glyph.** The glyph behind the panda is a drawing of a branch (a trunk, a curved branch and three nodes), not a copy of an official logo. Before the public release it has not yet been compared with the Git project's logo and trademark terms, which could not be read while building this; that check belongs before a public release.
- **No generator.** The icon files are committed as finished images and are edited as images, not regenerated from code.

## String resources

- **Two paths.** Fixed text in a composable is `stringResource(R.string.x)` (or `pluralStringResource`). Text a ViewModel builds from the data layer's facts (an error with its status code, "2 new repos") is resolved in the ViewModel through `BaseViewModel.string`, so the wording decision stays in the ViewModel and the View receives a plain `String`.
- **Why not a startup-resolved table.** A `Strings` object filled once at launch saves a lookup that costs microseconds, but it is fixed to the language at launch, and every screen and test would need the global. `stringResource` follows configuration changes for free.
- **`StringResolver`, not a bare `Context`.** The base ViewModel injects a small interface with one implementation over the application's resources. JVM unit tests cannot read resources, so they register `FakeStringResolver`, which echoes the resource id and arguments, and assert that the right resource and arguments were chosen.
- **Known latency.** The ViewModel's mapped text is recomputed when the state holder emits, not when the screen is drawn, so after a live language change an error message stays in the old language until the next state change. Accepted: those messages are transient.
- **Facts below the ViewModel, wording above.** The data and model layers keep facts: an issue's `updatedAtMs`, the rate limit's `resetsInSeconds`, a mode's `queryValue`. The wording lives in the UI layer: `RelativeTime.kt` ("just now", "3h ago"), `RateLimitText.kt` ("45s", "2m 5s") and `IssueFilterText.kt` (the exhaustive `when`s that map each mode and language to its string resources).
- **Time-dependent text in a composable.** A "3h ago" line is worded when it is drawn, because the clock moves while the screen is open. A composable uses `relativeTimeText(ms)` or `resetsInText(seconds)`, which build on `rememberStringResolver()`. Generated text from a ViewModel still goes through `BaseViewModel.string`.
- **Old caches.** Issues saved before the timestamp was stored have no `updatedAtMs`, so they show "recently" until the repo is refreshed. Bookmarked issues are never refreshed, so older bookmarks keep showing "recently".
- **Left as symbols.** Glyphs such as ← ↗ ⌄ ☰ ✕ ★ and the "—" placeholder are drawing, not wording, and stay in code.

## Demo data

- **The token decides.** With no token the app shows demo data; with one it shows real data. The choice is made per call by small switching data sources (`SwitchedIssueSearchApi`, `SwitchedReadmeApi`, `SwitchedRepoIssueGroupStorage`), because a token can be added or removed while the app runs. Repositories and state holders are unchanged and never learn which source answered. The no-token screen and the `NoToken` results are gone: no token is no longer a dead end.
- **The data.** `data/demo/DemoData.kt`: sixteen invented repos (three or four for each of Kotlin, Java, Swift, JavaScript and Python) and 85 issues in both modes, so every language and mode shows something; every title starts "[Demo]" and update times are set relative to now, so the lists never look stale. The data is written as the DTOs GitHub returns so the real mapper handles them. Ids are negative, so a demo issue can never be mistaken for a real one. `DemoIssueSearchApi` reads the same `label:`, `language:` and `repo:` qualifiers the real API is sent, so language filtering and a single repo's refresh behave as usual. It reports no rate limit, so the chip stays "—". `DemoReadmeApi` returns a short README in the Contents API's base64 form.
- **Cache isolation.** Demo results are cached in memory (`InMemoryRepoIssueGroupStorage`), never in the real cache file. Clear Cache clears the cache in use.
- **Tag on saved items.** `Issue.tag` (and `HiddenIssue.tag`) is null for real data and "demo" for demo data, and is saved with the item. `ApiTokenRepository.activeTag` is the tag of the data in use (none with a token, "demo" without). The Bookmarks and Hidden view models list only the entries whose tag equals it, so each mode sees only its own; the other mode's entries stay saved and reappear when that mode is back. Unhide all only touches the data in use. Screens never mention demo.
- **Marker.** A small "Demo data" chip (`DemoChip`) shows while there is no token. On Top Repos it takes the place of the rate-limit chip (there are no rate-limit numbers in demo mode) and a tap explains the missing token, with a way to Settings and to the token guide. On the repo issues screen it sits in the title bar beside the open-in-browser icon. There is no banner: getting a token is the welcome screen's job.
- **Switching reloads.** `TopReposStateHolder` reloads the list when the tag flips, from the cache of the data now in use.
- **Known loose ends.** A demo issue's link points at a github.com address that does not exist. Demo bookmarks and hidden entries live in the real bookmarks and hidden files, hidden by the filter rather than stored elsewhere.

## Token storage

- **One token, two sources.** The token is always the same thing: a GitHub personal access token. The app gets it from the user (typed on the welcome screen or in Settings) or, in a debug build only, from the developer's `local.properties` (the "build token"). The user's wins when both exist. The build token is compiled into the debug app and is never written to storage; the user's token is the only one the app stores.
- **Who is at risk, and from what.** The token the guide asks for has no permissions, so it reads public data and nothing else; the worst a leak could do is spend its rate limit. Android already makes extracting it hard: app storage is encrypted at rest on a locked phone, no other app can read it without root, and release builds cannot be inspected with debugging tools. The remaining exposures are a copied or backed-up file, and a user who pastes a token that does have permissions. A warning for that was considered and dropped: GitHub reports a classic token's permissions in a response header, but not a fine-grained token's, so the check would have a hole.
- **Encryption.** `EncryptingApiTokenStorage` wraps the existing storage; `KeystoreTokenCipher` is AES-GCM with a key Android generates inside its Keystore and never lets the app read out, so a copy of the saved file is useless without the phone. It does not stop code running as the app, or a rooted phone. A saved value that cannot be decrypted (a token saved before encryption existed, a damaged value, a lost key) counts as no token and is wiped, and the user is asked again. If encrypting fails, nothing is written (never plain text) and the token lasts until the app closes. The saved file is also excluded from backups and device transfer. The decorator is tested on the JVM with a fake cipher; the real Keystore round trip is a device test.
- **Masking.** `TokenField` is the one text box for the token, on the welcome screen and in Settings. It shows dots until the user taps Show, uses the password keyboard type with auto-correct off so the keyboard does not learn it, and starts masked on every visit. Both screens start the field with the token in use, so a user can see one is set.
- **Removing.** "Remove my token" (Settings and the welcome screen, shown while a user token is saved) deletes the stored value. It falls back to the build token if the build has one; the app cannot remove what is compiled into it. So a debug build with a build token never reaches the no-token state; to see the welcome screen as a new user does, build without the token or use a release build.
- **Release builds never carry the build token.** The token is in `BuildConfig` for debug variants only; release variants always get an empty string, because a published app can be unpacked by anyone and every user would share the token. `scripts/check-release-has-no-token.sh` (also run by CI) passes a made-up token, requires the debug builds to contain it (so the check cannot pass by looking in the wrong place), and fails if either release build does.
- **Where the token goes.** Only to GitHub's API, in the Authorization header; the HTTP library drops the header on a redirect to another host. It is not logged (HTTP logging is off in release; in debug it logs the method, URL and status only). Plain-text connections are not allowed.

## Build flavors

- **Why flavors now.** The project is published two ways from one codebase: `foss` for GitHub and `commercial` for Google Play. Plain build-time booleans remain right for developer aids such as the detailed drawer menu, but a flavor is the only way to keep code that just the commercial build may contain out of the open build at compile time; a runtime flag would leave it in the open APK.
- **Ids.** `io.github.genesjc.opensourcepanda` (foss) and `io.github.genesjc.opensourcepanda.commercial`, written out in full in `app/build.gradle.kts` rather than derived, because a published Play id cannot change. The code package and the `namespace` are `io.github.genesjc.opensourcepanda`, replacing the `com.example` placeholder; users never see either.
- **Which variant is running.** The Gradle console ends with `Build A.B (commercialDebug)` for the variant that was built or installed (Android Studio uses the variant's own tasks, such as `installCommercialDebug`), and the Top Repos menu header shows `Build A.B (commercial)`. On a device, `adb shell pm list packages | grep opensourcepanda` lists the installed application ids.
- **The builds must stay clean.** `scripts/check-no-ads-sdk.sh` (also run by CI) fails if either flavor lists an ads or consent library, or has an ads entry in its merged manifest. See "Advertising (parked)".
- **Side effects.** Variants are `fossDebug`, `commercialDebug` and so on; CI names both flavors (`testFossDebugUnitTest testCommercialDebugUnitTest`, `assembleFossDebug assembleCommercialDebug`), because the bare `testDebugUnitTest` is ambiguous with two flavors.

## Advertising (parked)

- **Where it stands.** Ads are parked: no build contains the ads SDK or any code that depends on it. The ads layer was built and merged, then taken out of the build because the ad account, privacy and consent work behind it is not finished. The working implementation is kept in the repository's history, and `docs/ads-restore.md` says exactly where.
- **What was removed, and what stayed.** Removed: the SDK dependency, the real controller, the ad-free period, the real banner, the AdMob manifest entry, the ads ids and production guard in the build file, the ads build-config fields, the ads-only tests and strings, and the backup rules for the ad-free period. Kept: the SDK-free hooks (the `AdsController` interface and `NoAdsController`, the banner slot, the offer line, the ViewModel flows and the menu entries), which show nothing while the flags are false. The commercial flavor keeps small stubs (a module binding the do-nothing controller, and an empty banner) that restoring overwrites.
- **Why park, and not a switch or a flavor.** A switch that binds a do-nothing controller leaves the SDK, its permissions and its manifest entries in the app file, which store declarations are judged against. Making the switch remove the SDK needs conditional source sets or modules and an IDE blind spot for the code that is off; a third flavor multiplies every variant. Parking is simpler and has no drift to maintain. A long-lived branch was rejected for the same reason: it falls behind the main line. The archived history is frozen, and restoring copies files out of it and re-checks the integration points.
- **The clean-build check.** `scripts/check-no-ads-sdk.sh` (also run by CI) fails if either flavor's release classpath lists an ads or consent library, or its merged manifest has an AdMob entry or the advertising-id permission. With ads parked there is no build to use as a positive control; the restore guide brings the old control back with the code.
- **The way back.** `docs/ads-restore.md` (procedure, with every removed build block in full) and `docs/ads-architecture.md` (how the layer works, the ad-free hour, edge cases and testing). `docs/ads-testing-rules.md` holds the rules for when ads are live.

## Branching workflow

- **Feature sets.** Each feature set uses `feature-set/<name>` as staging and `refinement/<name>` for the work, with one commit per step, so a failing step points at one commit. Both are deleted after the merge into `develop`, the default branch. The README's "Which branch?" note tells a reader what `develop` and `main` hold.
